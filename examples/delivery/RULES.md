# 데모배달 주문 추적 데모 — 규칙 명세

> **승인 상태:** 사용자가 요청에서 "명세는 파일로 쓰고 바로 진행해, 확인 안 받아도 돼"라고 사전 승인함. 아래 기본값·가정으로 진행했고, 마지막 "가정" 절은 데모데이 전에 확인 필요.

## 브리프에서 이미 정해진 것
- 목적: 투자자 데모데이. 자동 재생으로 정상 흐름을 보여주고, 질문이 나오면 발표자가 상황을 바꿔가며 설명.
- 플로우: 주문 접수 → 가게 수락(또는 거절) → 조리 중 → 라이더 배차 → 픽업 → 배달 중(지도에서 라이더 이동) → 배달 완료 → 리뷰 요청.
- 예외 5가지: 가게 거절 시 자동 환불 / 배차 5분 초과 시 지연 안내 + 쿠폰 / 조리 시작 전까지만 고객 취소 / 배달 중 주소 변경은 라이더 승인 필요 / 라이더 통신 끊김 시 마지막 위치 표시.
- 실제 30~40분 걸리는 흐름을 1분 안에. 시안 없음. 모바일.

## 적용한 기본값 (질문 대신)
| 항목 | 기본값 |
|---|---|
| 기기 | 모바일 390×844 프레임, 화면 폭에 맞춰 축소 |
| 디자인 | 시안 없음 → 중립 UI + 브랜드 컬러(주황 #FF6B2C), 가상의 앱 "데모배달" |
| 언어 | 한국어 |
| 시연 방식 | 자동 재생 프리셋 + 발표자 콘솔(단축키 포함) 둘 다 |
| 가짜 처리 | 결제·환불·쿠폰·지도·라이더 위치·가게/라이더 응답 전부 메모리 시뮬레이션 |
| 배포 | 정적 파일 zip, 디스크에서 바로 열림, 오프라인 동작 |
| 이후 용도 | 일회성 데모 (빌드 없는 정적 스택) |

## 시간 압축 (핵심)
- **이야기 시계: 실제 1분 = 데모 1초 (60배).** 앱 상태바 시계는 19:00에서 시작해 데모 1초마다 1분씩 간다.
- 모든 규칙(배차 5분 기준 포함)은 이 이야기 시계로 **정확히** 적용된다. 4분 59초에는 쿠폰 없음, 5분 00초에 지급.
- 정상 흐름: 주문 → 30분 뒤 배달 완료 → 31분 리뷰 요청 = 데모 약 36초.
- 일시정지(P)는 이야기 시계까지 멈춘다. 다음(N)은 남은 대기를 건너뛴다.

## 불변식
- 진행 중 주문은 하나. "주문하기"를 여러 번 눌러도 ORD id는 하나.
- 주문 id는 통신 끊김·주소 변경·화면 이동에도 바뀌지 않는다.
- 조리가 시작된 주문은 고객이 취소할 수 없다.
- 환불은 거절·취소 시에만, 주문당 한 번.
- 쿠폰은 배차 대기 5분 도달 시 주문당 한 번. 이미 배차되면 지급 안 함.
- 주소는 라이더 승인 없이 바뀌지 않는다.
- 통신이 끊긴 동안 앱은 새 위치를 보여주지 않는다(마지막 위치 고정).
- 라이더 통신 끊김은 배차된 라이더가 있을 때만 존재한다.

## 예외
| 상황 | 화면 동작 | 규칙 |
|---|---|---|
| 가게 거절 | "가게가 주문을 받을 수 없어요" + 환불 카드 | 접수 상태에서만 거절 가능, 즉시 자동 환불 |
| 가게 무응답 | 계속 "가게 확인 중" | 데모에서는 자동 취소 없음 (발표자 설명용으로 대기 유지) |
| 배차 5분 초과 | 지연 안내 배너 + 3,000원 쿠폰 카드, 예상 시간 +10분 | 5:00 정확히 지급, 주문당 1회 |
| 조리 후 취소 시도 | "조리가 시작되어 취소할 수 없어요" 안내 | 상태 변화 없음 |
| 주소 변경 대기 중 통신 끊김 | 요청은 "라이더 확인 대기" 유지 | 라이더 응답은 통신 복구 후에만 |
| 주소 변경 거절 | "기존 주소로 배달해요" | 주문당 1회라 재요청 불가 |
| 통신 끊김 중 도착 | 지도는 마지막 위치, 상태는 "배달 중" | 복구 시 완료 처리 |
| 주문하기 연타 | 첫 탭만 주문 생성 | 이후 "이미 진행 중인 주문이 있어요" |
| 진행 중 메뉴 화면 이동 | 상단에 "진행 중인 주문 보기" 배너, 주문 버튼 비활성 | 같은 주문 유지 |

## 시나리오 (자동 재생 프리셋)
| 키 | 제목 | 단계 |
|---|---|---|
| 1 A | 정상 배달 (데모데이 본편, 약 35초) | 메뉴 2s · 주문 접수 2s · 가게 수락 2s · 조리 시작·배차 탐색 3s · 배차·가게로 이동 9s · 픽업·배달 중 13.3s · 배달 완료 1s · 리뷰 요청 2.5s |
| 2 B | 가게 거절 → 자동 환불 | 메뉴 · 접수(가게 수동) · 거절 → 환불 |
| 3 C | 배차 지연 → 안내 + 쿠폰 | 라이더 부족 · 접수 · 수락 · 탐색 5분 · 지연 안내+쿠폰 · 수급 회복 → 배차 · 가게로 이동 · 픽업 |
| 4 D | 고객 취소: 조리 전 가능 / 조리 후 불가 | 주문1 수락 후 취소 → 환불 · 주문2 조리 중 취소 시도 → 불가 |
| 5 E | 배달 중 주소 변경 (라이더 승인) | 배달 중까지 빨리 감기 · 주소 변경 요청 · 라이더 승인 → 경로 변경 · 회사 도착 |
| 6 F | 라이더 통신 끊김 → 마지막 위치 | 배달 중까지 빨리 감기 · 통신 끊김 · 복구 → 위치 갱신 · 배달 완료 |

"빨리 감기"는 같은 규칙 엔진을 가상 시계로 즉시 돌린 것 (타임라인에 모든 이벤트가 남는다).

## 가짜 처리
- 결제·환불·쿠폰: 화면 표시만. 실제 결제 없음.
- 지도: 가상 동네 SVG. 실제 지도·GPS·주소 없음.
- 가게·라이더 응답: 시간 규칙 또는 발표자 콘솔.
- 인물·상호·주소 전부 가상 ("한입분식", "김바람 라이더", "데모구 샘플로 12").
- 새로고침하면 처음부터.

## 가정 (확인 필요)
1. 라이더 배차는 조리 시작과 동시에 탐색한다(실제 배달앱 방식). 이벤트 순서는 브리프대로 조리 → 배차 → 픽업으로 보인다.
2. "배차 5분"은 배차 탐색 시작(=조리 시작)부터 잰다. 주문 시점부터가 맞다면 기준점만 바꾸면 됨.
3. 지연 쿠폰은 3,000원, 예상 시간 +10분 안내.
4. 고객 취소 가능 구간 = 주문 접수 + 가게 수락(조리 시작 전). 가게 거절은 접수 상태에서만.
5. 주소 변경은 배달 중에만, 주문당 1회, 대체 주소는 "회사" 하나. 추가 배달비 없음.
6. 통신 끊김 중 도착/픽업은 통신 복구 시점에 반영(라이더 앱이 보관 후 전송).
7. 가게 무응답 자동 취소는 넣지 않음(발표 중 대기 상태를 유지하기 위해).
8. 고객 쪽 네트워크 끊김은 브리프에 없어 다루지 않음.
